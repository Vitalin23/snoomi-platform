# PRD: Клиентский экспертный AI-агент для генерации контента

Версия: 1.0  
Дата: 2026-02-10  
Статус: Draft for implementation

---

## 1) Контекст и проблема

Текущий контур генерации контента работает, но:

- иногда уходит в бизнес-описание клиента (например, "продвижение магазина"), а не в пользовательскую ценность;
- не всегда стабильно поддерживает экспертный уровень в нише клиента;
- не всегда опирается на системное "знание домена" (семантика, реальные вопросы аудитории, источники);
- недостаточно прозрачно управляет качеством и фактологией до публикации.

Нужен **персонифицированный контент-агент по каждому клиенту/каналу**, который:

1. глубоко изучает тематику канала;
2. собирает семантическое ядро и актуальные вопросы аудитории;
3. использует внешние источники;
4. пишет платформенно-адаптированные экспертные тексты;
5. проходит quality-gate до публикации.

---

## 2) Цели и не-цели

### 2.1 Цели

1. Повысить релевантность тем и текстов тематике канала.
2. Обеспечить платформенную адаптацию (VK/TG) без "копипаста".
3. Ввести управляемый контур качества (факты/стиль/структура/читабельность).
4. Создать масштабируемую архитектуру "обучения" через память и retrieval, а не ручной хаос промптов.
5. Сократить процент неудачных генераций и ручных правок.

### 2.2 Не-цели (на первом этапе)

1. Не делать отдельный fine-tune LLM под каждого клиента.
2. Не строить полноценный универсальный "автономный AGI-агент".
3. Не расширять сразу на новые платформы (фокус: Telegram + VK).

---

## 3) Продуктовая гипотеза

Если агент перед генерацией:

- формирует и поддерживает семантическое ядро клиента,
- извлекает проверенный контекст из базы знаний + свежих источников,
- пишет по платформенным правилам,
- и проходит quality-gate,

то качество контента и полезность для аудитории вырастут, а доля ручных правок снизится.

---

## 4) Архитектура (target state)

## 4.1 Высокоуровневые компоненты

1. **Ingestion Layer**  
   Сбор данных:
   - посты канала клиента;
   - описание и style-сигналы;
   - подобные каналы;
   - тематические статьи и публичные источники;
   - вопросы аудитории из поиска/форумов/Q&A.

2. **Knowledge Layer**  
   Хранилище:
   - исходники (raw + normalized),
   - embeddings/векторный индекс,
   - метаданные источников (дата, авторитет, тематика).

3. **Semantic Core Builder**  
   Построение:
   - кластеры тем;
   - интенты (инфо/сравнение/коммерция/вовлечение);
   - боли/задачи аудитории (JTBD);
   - словарь терминов клиента.

4. **Orchestrator (Agent Pipeline)**  
   Шаги:
   - Researcher -> Planner -> Writer -> Fact-checker -> Style editor.

5. **Quality Gate**  
   Автоскоринг:
   - релевантность теме;
   - фактологичность;
   - соответствие платформе;
   - читаемость и длина;
   - safety/risk checks.

6. **Publishing Layer**  
   Публикация + логирование + обратная связь.

## 5) "Обучающийся агент": стратегия реализации

### 5.1 Почему не per-client fine-tune на старте

Fine-tune под каждого клиента дорогой, сложный в поддержке, плохо масштабируется и медленно обновляется.

### 5.2 Что делаем вместо этого

**RAG + memory + evaluation loop**

- RAG: агент извлекает релевантный контекст из базы знаний клиента.
- Memory: хранит профиль канала, tone, ограничения, удачные шаблоны.
- Evaluation loop: после публикаций учитывает метрики и фидбек, корректирует стратегию.

Это и есть практическая "обучаемость" в проде.

## 6) Data Model (предложение)

Новые сущности (логические; можно хранить в текущей БД или отдельном storage):

1. `knowledge_source`
   - `id`, `client_id`, `channel_id`, `source_type` (channel_post/web/article/competitor),
   - `url`, `title`, `published_at`, `fetched_at`, `authority_score`, `lang`.

2. `knowledge_document`
   - `id`, `source_id`, `chunk_index`, `text`, `embedding_vector_ref`,
   - `keywords`, `entities`, `summary`.

3. `semantic_cluster`
   - `id`, `client_id`, `channel_id`, `cluster_name`, `intent_type`,
   - `priority`, `seasonality`, `updated_at`.

4. `audience_question`
   - `id`, `client_id`, `channel_id`, `question_text`,
   - `source_ref`, `trend_score`, `last_seen_at`.

5. `generation_run`
   - `id`, `client_id`, `channel_id`, `topic`, `platform`, `run_mode`,
   - `input_context_ref`, `output_text`, `output_image_ref`,
   - `quality_score`, `status`, `error`, `created_at`.

6. `quality_report`
   - `id`, `run_id`, `relevance_score`, `fact_score`, `style_score`, `format_score`,
   - `risk_flags`, `decision` (approve/revise/reject), `created_at`.

7. `editor_feedback`
   - `id`, `run_id`, `feedback_type`, `comment`, `accepted`, `created_at`.

## 7) Агентный pipeline (E2E)

1. **Input**: канал + тема (или тема из плана) + платформа.
2. **Retrieve**:
   - топ релевантных кластеров семантики,
   - топ свежих документов,
   - топ вопросов аудитории.
3. **Plan**:
   - тезисы,
   - угол подачи,
   - структура поста под платформу.
4. **Draft**:
   - генерация текста в заданных ограничениях длины.
5. **Fact-check**:
   - проверка фактов/дат/заявлений против retrieved-контекста.
6. **Style pass**:
   - выравнивание под tone/словарь бренда/запреты.
7. **Quality Gate**:
   - если score ниже порога -> revise loop.
8. **Publish**:
   - текст + изображение,
   - запись run + итоговых метрик.

---

## 8) Платформенные правила генерации (обязательные)

### 8.1 VK

- hook в первых строках;
- короткие абзацы + списки;
- 1 CTA;
- вопрос на вовлечение;
- 2-5 релевантных хэштегов;
- без перегруза внешними ссылками.

### 8.2 Telegram

- сильная первая мысль;
- короткая плотная подача;
- мягкий CTA;
- единый пост с медиа;
- контроль длины подписи/поста под ограничения Telegram.

---

## 9) Quality Gate: KPI и пороги

### 9.1 Автоскоры (0..1)

- `relevance_score` >= 0.80
- `platform_fit_score` >= 0.85
- `style_match_score` >= 0.75
- `fact_consistency_score` >= 0.75
- `readability_score` >= 0.70

Если любой критичный ниже порога -> revise.

### 9.2 Продуктовые KPI

1. Доля публикаций без ручной правки.
2. Среднее число правок на 1 пост.
3. Engagement delta (сравнение до/после).
4. CTR/сохранения/комментарии/подписки по темам.
5. Доля "провалов релевантности" (manual flag).

## 10) API-контракты (предложение)

1. `POST /api/agent/semantic-core/rebuild`
   - rebuild семантики клиента/канала.

2. `POST /api/agent/research/update`
   - обновление внешних источников и вопросов.

3. `POST /api/agent/draft`
   - генерация черновика (platform-aware).

4. `POST /api/agent/quality/evaluate`
   - quality report и решение.

5. `POST /api/agent/publish`
   - публикация approved draft.

6. `GET /api/agent/runs`
   - история запусков с quality/ошибками.

## 12) Риски и mitigation

1. **Галлюцинации и устаревшие факты**  
   -> retrieval only + факт-чек + freshness filter.

2. **Уход в "продвижение магазина" вместо пользы аудитории**  
   -> разделение бизнес-целей и контент-интентов в data model + prompt constraints.

3. **Сетевые сбои при публикации медиа**  
   -> retry/backoff/адаптивное сжатие/fallback delivery.

4. **Рост стоимости генерации**  
   -> кэширование результатов research/semantic, батч-режимы, лимиты на regenerate.

---

## 13) Безопасность и комплаенс

- хранение токенов только в защищенном конфиге;
- маскирование чувствительных данных в логах;
- ограничение источников (denylist + allowlist по доменам при необходимости);
- аудит изменений и публикаций (кто/когда/что отправил).

---

## 14) Definition of Done (этап v1)

Решение считается готовым, если:

1. для каждого канала строится и обновляется semantic core;
2. агент генерирует платформенно-адаптированные тексты на основе retrieval;
3. перед публикацией есть quality report и пороговый gate;
4. результаты и фидбек доступны в интерфейсе;
5. KPI качества стабильно улучшаются в течение 2-4 недель наблюдения.
